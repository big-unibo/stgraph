SmartBench evaluation: inconsistencies to examine
=================================================


1. Queries
----------

General


EnvironmentOutlier



- Graphix: wrong result, NOT FIXED (engine bug). In AsterixDB 0.9.9 (both the one of STGraph and the one of
  Graphix), st_geom_from_text (and st_geom_from_geojson) returns, for every row of a query, the geometry of the first
  row (SELECT VALUE st_as_text(st_geom_from_text(s)) FROM ["LINESTRING(34 0, 63 20)", "LINESTRING(4 15, 9 19)"] AS s
  returns the first line twice; constants work). STGraph is not affected: it sends one constant WKT per query. The
  Graphix query converts the location of every environment in the same query, so every environment gets the line of
  the first one: on small 1 environment instead of 4 (without the spatial condition, Graphix returns the same 4
  environments as STGraph). Which environment is "the first one" depends on the plan: with the series vertices (see
  below) it is another one, and on small the result has 0 environments above the threshold instead of 1. A fix would
  store the environments as geometries at load time, through a data feed (the feeds parse WKT one record at a time;
  an INSERT cannot convert a string into a geometry field).

- Graphix, all queries: FIXED (model). The graph had one Temperature vertex per event (an edge per event, through a
  join of TimeSeries and Observations): every query scanned all the events twice (the edge and the vertex) and
  joined them on (tsid, _id), with hash joins. On large (259,200,000 events) EnvironmentCoverage did not end in two
  days, on 1 core. Now, as in STGraph (and PGAge), a time series is one vertex (a record of TimeSeries), and the
  queries join the series found in the graph with Observations on tsid, with the time window on _id. On small, same
  results as before, row by row (EnvironmentOutlier without the spatial condition, see above).

- Graphix, events of a series: NOT FIXED (limit of the system). The queries do not read the events of a series by
  the primary key (tsid, _id), as STGraph does, but scan Observations once per query (hash join). The optimizer of
  Graphix uses an index in a join only with a hint (/*+ indexnl */), which the queries do not use (the other
  systems choose their plans by themselves), and its cost-based optimizer does not run: the plan is the same after
  ANALYZE DATASET, also for a plain SQL++ join, and SET `compiler.cbo` "true" fails (IndexOutOfBoundsException).
  The AsterixDB 0.9.9 of STGraph does it by itself: after ANALYZE DATASET, the same join (a series dataset and the
  events of STGraph) becomes a search on the primary key, without hints. STGraph does not depend on it: it sends
  each series its own query, with the tsid as a constant. With the hints, a range search per series on (tsid, _id):
  on small, e.g. AgentOutlier 4.7 s instead of 6.9 s, AgentHistory 0.3 s instead of 2.7 s (throwaway container,
  1 core); on large, a scan of 259,200,000 events per query.


2. Loaders (Kotlin port vs Python code)
---------------------------------------

Timing


  One difference left, forced by the engine: the AsterixDB of Graphix (0.9.9-SNAPSHOT) stores the last, partial
  frame of a feed only when the feed stops, while the 0.9.9 of STGraph stores it with the feed open (checked on
  small: 2,591,904 of 2,592,000 events readable before STOP FEED, all of them after; same client, 1,000 events:
  1,000 readable with the socket open on the 0.9.9, 896 on the AsterixDB of Graphix). So each Graphix worker closes
  its feed (as STGraph closes its feeds) before waiting for its last event, once AsterixDB has read its whole stream
  (half-closed socket, AsterixDB closes its side at the end of the stream: stopping a feed that is still reading
  loses the unread events). The wait until the stream is read is time-series time, as the rest of the wait; the
  close (STOP FEED) is index time, as in STGraph.
  Graphix cannot run on the AsterixDB 0.9.9 of STGraph: it needs Hyracks and Algebricks changes that never reached
  a release (graphix-asterixdb/mirror), and its jar does not load on the 0.9.9 (NoSuchMethodError).
  The Graphix ingestions in results/ before this change are not comparable with STGraph.

PGAge
- String values are not escaped: an apostrophe in a value makes the whole entity fail (it is logged and skipped).
- Batch insert: one INSERT of 20,000 rows (execute_values) in Python, JDBC batches rewritten into multi-row INSERTs
  (reWriteBatchedInserts) here.
- Not ported: multi-device entities and GeoJSON locations (SmartBench has neither).

Neo4j

- The events have a range index on Temperature.timestamp, the temporal index of the other systems, built after the
  load (index time); the Python code did not create it. No index on the ids of the entities (e.g., Sensor.id, used
  by every UNWIND batch and by the MATCH (v {id: ...}) of the dumps), as PGAge has none on its graph.

- The dumps are read from datasets/original/smartbench/neo4j/<size> (./downloadDataset.sh smartbench/neo4j <size>);
  their names may follow the old sizes (see below).


3. Configuration and infrastructure
-----------------------------------
- Sizes: the old time_constraints_tstamp.yaml used small/large/big/big_long; time_constraints.yaml of STGraph has the
  same windows as small/medium/large (large -> medium, big -> large), plus xsmall and extralarge. FIXED: the
  evaluation runs AeonG and HyGraph with the old names (small -> small, medium -> large, large -> big).
- Neo4j: the old image was FROM neo4j (latest at build time); the compose now pins neo4j:5.26 (conf with server.*
  keys, so 5.x). OPEN: check the version used for the paper.
- PGAge: the Dockerfile clones apache/age master (not pinned). OPEN.
- PGAge: conf/postgresql.conf preloads only timescaledb (AGE is loaded per session). The original evaluation set
  shared_buffers = 64 GB and effective_cache_size = 193 GB. FIXED: they are the defaults of PostgreSQL now.
- Memory: Neo4j has a page cache of 512 MB (conf/neo4j.conf), the other systems their defaults. OPEN.
- AeonG and HyGraph run their client inside their container, limited to one core: client and database share it,
  while the client of STGraph, Neo4j, PGAge and Graphix (the evaluation) runs outside the container of the database.
  OPEN.
- HyGraph compose: chmod +x scripts/run_evaluation.sh.sh (typo); scripts/run_evaluation.sh runs
  python3 evaluate_hygraph.py from /hygraph, while the file is in src/smartbench/. OPEN.
